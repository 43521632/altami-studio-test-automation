# Инструкция для AI — проект автотестов Altami Studio

## 1. Цель

Переделать текущие тесты так, чтобы они были **изолированы друг от друга**. Каждый тест должен запускаться из гарантированно чистого состояния приложения (не ВМ).

**Архитектура:**
1. **Однократная подготовка ВМ** (до всех тестов): восстановление снапшота, получение установщика, запуск ВМ.
2. **Один тест установки** — устанавливает приложение, выполняет первичную настройку, закрывает приложение.
3. **Все остальные тесты** — запускают приложение, проверяют, закрывают. Каждый тест начинается с чистого запуска и не влияет на другие.

**Источники данных:**
- Ревизия сборки — из CI (переменная `BUILD_REVISION`), аргумент `--revision` или **из Kiwi TCMS** (через API).
- Версия продукта — из CI (`APP_VERSION`), аргумента `--app-version` или файла `VERSION` в корне проекта.
- Установщик — скачивается с `https://cache.altami.ru/artifactory/app-builds/altami/{revision}/{platform}/AS_{version}_{revision}_{platform}.{ext}`.
- Аутентификация — логин/пароль из `CACHE_USER`/`CACHE_PASSWORD`.

## 2. Интеграция с Kiwi TCMS

### 2.1. Общая концепция

- **Тест-раны создаются вручную** в Kiwi TCMS (через UI). Автотесты их не создают.
- **Каждый тест в коде сопоставлен с ID кейса** в Kiwi через `src/case_ids.py`.
- **Автотесты обновляют существующие тест-раны**: добавляют результаты для каждого кейса и прикрепляют артефакты (лог, скриншоты, diff).
- **По завершении тест-ран автоматически закрывается** (опция).

### 2.2. Реализованные компоненты

| Файл | Назначение | Статус |
|------|------------|--------|
| `utils/kiwi_client.py` | Клиент для API Kiwi TCMS (аутентификация, получение ревизии, отправка результатов) | ✅ **Реализован полностью** (через `tcms-api`) |
| `utils/pytest_kiwi_plugin.py` | Плагин pytest для сбора результатов и отправки в Kiwi | ✅ Готов |
| `utils/config.py` | Получение ревизии из Kiwi (приоритет: BUILD_REVISION → --revision → Kiwi) | ✅ Готов |
| `tests/conftest.py` | Подключение плагина `pytest_kiwi_plugin` | ✅ Готов |

### 2.3. Переменные окружения для Kiwi

| Переменная | Назначение | Обязательность |
|------------|------------|----------------|
| `KIWI_URL` | URL Kiwi TCMS (например, `https://kiwitcms.altami.ru`) | Да |
| `KIWI_USER` | Логин (используется для аутентификации и проверки назначения) | Да |
| `KIWI_PASSWORD` | Пароль | Да |
| `KIWI_TESTRUN_ID` | ID тест-рана (если задан, ревизия получается из Kiwi, результаты отправляются в этот тест-ран) | Нет (но нужен для отправки) |
| `KIWI_REPORTING_ENABLED` | Включить/отключить отправку (по умолчанию `true`) | Нет |
| `KIWI_SKIP_IF_UNAVAILABLE` | Если `true`, при недоступности Kiwi не падать, а сохранять локально (по умолчанию `true`) | Нет |

### 2.4. Как работает получение ревизии

1. Приоритет: `BUILD_REVISION` → `--revision` → Kiwi (через `KIWI_TESTRUN_ID`).
2. Если задан `KIWI_TESTRUN_ID`, клиент Kiwi:
   - Аутентифицируется на `KIWI_URL` с логином/паролем.
   - Запрашивает тест-ран по ID через API `/api/v1/testruns/{id}/`.
   - Проверяет, что тест-ран назначен на пользователя `KIWI_USER` (поле `assignee` или `owner`).
   - Если назначение совпадает — извлекает ревизию из поля `build`.
   - Если не совпадает — возвращает `None` (ревизия не найдена).

### 2.5. Как работает отправка результатов

1. Плагин `pytest_kiwi_plugin` собирает для каждого теста:
   - ID кейса (из `src/case_ids.py`).
   - Статус (PASS/FAIL/SKIP).
   - Комментарий (сообщение об ошибке).
   - Аттачменты: скриншоты (из `SCREENSHOT_DIR`), лог (из `logs/`), diff-изображения.
2. Для каждого теста вызывается `kiwi_client.add_case_result()`.
3. После завершения всех тестов вызывается `kiwi_client.close_testrun()`.
4. Если Kiwi недоступен, результаты сохраняются локально в JSON-файл (`kiwi_results_*.json`).

### 2.6. Реализованная интеграция с Kiwi TCMS (выполнено)

**Все API-запросы в `utils/kiwi_client.py` реализованы через официальную библиотеку `tcms-api`:**
- `add_case_result()` — добавление результата для кейса (обновление статуса и комментария).
- `close_testrun()` — закрытие тест-рана (установка `stop_date`).
- `upload_attachment()` — загрузка аттачмента (через Base64).

**Карта статусов Kiwi (для корректного отображения):**
| Статус в коде | ID в Kiwi | Название в Kiwi |
|---------------|-----------|-----------------|
| `PASS`        | 4         | PASSED          |
| `FAIL`        | 5         | FAILED          |
| `ERROR`       | 7         | ERROR           |
| `SKIP`        | 6         | BLOCKED         |

**Используемый XML-RPC endpoint:** `https://<KIWI_URL>/xml-rpc/`

## 5. Как использовать новую систему

### 5.1. Локальный запуск с указанием ревизии
```bash
pytest tests/ --revision=88034f7d4 --app-version=4.2.0
```

### 5.2. Использование локального установщика (без скачивания)
```bash
pytest tests/ --installer-path=/path/to/AS_4.2.0_88034f7d4_windows-x86_64.exe
```

### 5.3. Запуск только теста установки
```bash
pytest tests/test_install.py
```

### 5.4. Запуск конкретного теста с ID
```bash
pytest tests/ --case TC-85
```

### 5.5. Запуск с отправкой результатов в Kiwi
```bash
export KIWI_URL="https://kiwitcms.altami.ru"
export KIWI_USER="ваш_логин"
export KIWI_PASSWORD="ваш_пароль"
export KIWI_TESTRUN_ID=12345
export VM_ID=windows   # или astra
pytest tests/
```

### 5.6. Запуск с отключённой отправкой в Kiwi
```bash
export KIWI_REPORTING_ENABLED=false
pytest tests/ --revision=88034f7d4
```

### 4.4. Локальная разработка и режим разработчика

#### Текущие возможности локального запуска

В текущей архитектуре **уже предусмотрена** возможность локальной разработки без привязки к CI и без автоматического создания тест-ранов в Kiwi:

1. **Аргументы командной строки pytest**:
   - `--revision` – указать ревизию вручную.
   - `--app-version` – указать версию продукта.
   - `--installer-path` – использовать локальный установщик (скачивание пропускается).
   - `--case` – запустить только определённые тесты по ID.

2. **Переменные окружения для Kiwi** (опциональны):
   - `KIWI_REPORTING_ENABLED=false` – полностью отключить отправку результатов в Kiwi.
   - `KIWI_SKIP_IF_UNAVAILABLE=true` – если Kiwi недоступен, результаты сохраняются локально в JSON, а тесты не падают.

3. **Фикстуры** уже используют эти параметры и могут работать локально (скачивание установщика, подготовка ВМ – пока заглушки, но их можно доделать).

#### Режим разработчика

Для удобства локальной разработки предлагается добавить **режим разработчика** – специальный режим запуска, который:

- Автоматически отключает отправку в Kiwi (`KIWI_REPORTING_ENABLED=false`).
- Использует локальный кэш установщиков (уже реализовано в `utils/download.py`).
- Включает более подробное логирование (уровень DEBUG).
- Позволяет запускать только тесты, помеченные маркером `@pytest.mark.dev` (для быстрой итерации).

Режим разработчика активируется через аргумент `--dev` или переменную окружения `DEV_MODE=true`.

#### Скрипт-обёртка для локального запуска

Для упрощения запуска рекомендуется создать скрипт-обёртку `run_local.sh` (или `run_local.py`), который:

1. Проверяет наличие переменных окружения (ревизия, версия, путь к установщику).
2. Если не заданы – запрашивает их интерактивно.
3. Запускает `pytest` с соответствующими аргументами.

Пример такого скрипта можно добавить в корень проекта.

#### Как запускать локально прямо сейчас (без Kiwi)

```bash
# 1. Отключаем отправку в Kiwi
export KIWI_REPORTING_ENABLED=false

# 2. Указываем ревизию и версию (или используем локальный установщик)
pytest tests/ --revision=88034f7d4 --app-version=4.2.0

# Или с локальным установщиком (скачивание пропускается)
pytest tests/ --installer-path=/path/to/AS_4.2.0_88034f7d4_windows-x86_64.exe
```

Если Kiwi отключён, результаты сохраняются локально в `kiwi_results_*.json` (реализовано в `kiwi_client.py` как fallback).

#### Что нужно доделать для полноценной локальной разработки

Чтобы тесты реально запускались на локальной ВМ, необходимо:

1. **Реализовать копирование установщика на ВМ** (`copy_file_to_vm` в `utils/vm_operations.py`).
2. **Реализовать установку приложения** (`install_app` в `utils/app_operations.py`).
3. **Реализовать запуск/остановку приложения** (`start_app`, `stop_app` в `utils/app_operations.py`).

После этого фикстуры `prepare_environment`, `install_app` и `app_session` заработают, и вы сможете запускать тесты на своей локальной ВМ так же, как они будут работать в CI.

#### Приоритеты работ

1. **Интеграция с Kiwi TCMS** (реальные API-запросы) – **высший приоритет**, чтобы результаты тестов автоматически попадали в Kiwi.
2. **Реализация функций работы с ВМ и приложением** – чтобы тесты можно было запускать локально и в CI.
3. **Переключение существующих тестов на `app_session`** и дописывание теста установки.
4. **Добавление скрипта-обёртки и режима разработчика** – для удобства локальной разработки.

Такой порядок позволит сначала настроить интеграцию с Kiwi, затем обеспечить возможность локального запуска, а потом уже заниматься тестами.
